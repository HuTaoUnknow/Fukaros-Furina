# FUR2 加密信道

本文件描述 0.5.0 信道。工程版本为 0.5.0。明文 HMAC（0.4.x）不再兼容，也没有回退到明文。

## 选择

使用仓库内的 Monocypher 4.0.2（X25519、XChaCha20-Poly1305、BLAKE2b）以及 `core/crypto/` 里按 RFC 9382 实现的 SPAKE2（edwards25519、SHA-256、HKDF、HMAC）。没有使用 `QSslSocket`：当前工程没有现成的 OpenSSL 配置，Linux 与文档中的 Android Qt 构建都不应该再要求手工安装 OpenSSL。

SPAKE2 的口令不出现在报文里，也不发送 `HMAC(challenge, password)`。被动记录不能离线枚举口令。确认码不一致时，本次尝试的会话密钥会被清掉。

## 调用方传什么

`Peer::listen` / `Peer::connectTo` 的 `token` 参数保持原签名：

- **人类配对码**：至少 6 个字符、且不符合下面一次性格式的字符串。可重复使用，作为 SPAKE2 口令。
- **一次性二维码密钥**：`ot1.` 加 22 个无填充 base64url 字符（128 位）。同一进程内成功使用一次后再次传入会被拒绝，状态里不会打出密钥。`pairingListen` / `pairingConnect` 在 `OneTimeQr` 时把二维码字段 `s` 加上 `ot1.` 前缀再传入，并清掉已保存的长期密钥，使这次握手使用该一次性密钥。
- **长期密钥**：第一次配对成功后发出 `longTermKeyEstablished(QByteArray)`，内容是 32 字节。配对层把它写入安全存储，键名 `channel-long-term-key`。下一次手动配对前调用 `setLongTermKey`。设置之后，SPAKE2 用这 32 字节，不再使用 `token`。`Peer` 自己也会记住本次进程里刚协商出的密钥。一次性二维码配对不使用这份旧密钥。

`listen` 在调用方给出了地址时按该地址绑定。地址非法或实际绑定结果不一致时直接失败，不会改听 `0.0.0.0`。未传地址时才使用 `0.0.0.0`。

## 线路

多字节整数是大端，和现有 FUR1 头一致。SPAKE2 副本内部的 `len()` 仍按 RFC 9382 使用 8 字节小端。

双方先发送：

```text
"FUR2" || uint16 版本 = 2
```

版本不是 2，或前 4 字节不是 `FUR2`（包括 0.4.x 的 `FUR1`），立即失败。状态字符串会写明拒绝的是旧明文协议或未知版本。

接着是握手消息，格式为 `uint8 0 || uint8 类型 || uint16 长度 || 正文`：

| 类型 | 方向 | 正文 |
| --- | --- | --- |
| 1 | 双方 | 32 字节 SPAKE2 元素。客户端是 A（`furina-client`），服务端是 B（`furina-server`） |
| 2 | 双方 | 32 字节 HMAC 确认码 |
| 3 | 服务端 → 客户端 | 用握手密钥封装的 32 字节长期密钥 |
| 4 | 客户端 → 服务端 | 确认已经收下长期密钥 |

口令先做 `SHA-512("FUR2-SPAKE2-w-v2" || password)`，再对 edwards25519 的群阶取模，得到 SPAKE2 的 `w`。附加数据是 `FUR2-2`。长期密钥已设置时，这 32 字节本身就是口令。

确认通过后，从 `Ke || Ka` 用 HKDF-SHA256 派生：

- `main-c2s` / `main-s2c`：主连接两个方向的 32 字节 AEAD 密钥
- `cursor-base`：光标连接的基础密钥
- `ltk-wrap`：只用于上面的长期密钥封装

AEAD 是 Monocypher 的 XChaCha20-Poly1305。记录格式：

```text
uint8 版本 = 2 || uint64 计数器 || uint32 明文长度 || 密文 || 16 字节 tag
```

计数器从 0 递增。收到的计数器必须等于期望值，重放或乱序都会失败并清除本次密钥。nonce 把方向字符串（`F2mainC2`、`F2mainS2`、`F2cursC2`、`F2cursS2`）和计数器绑在一起。明文是一条原来的 FUR1 帧，`fr_type` 不变。

主连接进入数据阶段后，服务端先发送 `FR_READY`，双方再发送屏幕缩放能力。`Peer` 的 `listen`、`connectTo`、`sendVideo` 和原有信号都还在。

## 光标连接

光标 TCP 使用同一套 `FUR2` 头。双方交换 X25519 临时公钥，用主握手给出的 `cursor-base` 作为 HKDF 的 salt，确认后再进入独立的 AEAD 计数器。重连会生成新的临时密钥，因此不会复用已经用过的 nonce。光标包本身仍然用原来的 `fr_cursor_packet_valid` 检查。

## 监听与失败锁定

这些都在 `Peer` 内：

- 已经有主会话时，额外的接入不会变成第二路会话。主会话就绪后，最多保留一个光标候选；再多的直接丢掉。
- 每个远端地址以及全局都计数。5 次失败后锁定 5 分钟，下一轮再失败则加倍，最长 80 分钟。锁定期间的新连接直接拒绝。成功配对会清掉这一轮计数。日志和状态不会包含口令或长期密钥。

## 视频发送

`sendVideo` 在调用线程上只做校验和计数。加密和 socket 写入在 `Peer` 自己的 IO 线程。正在发送、尚未写完的视频帧最多 3 个；第 4 个返回 `false`，并像原来一样等待下一个关键帧。队列不会无限增长。码率仍由已有的 `FR_FEEDBACK` / `FR_PROFILE` 表达，这里没有另做一套码率协议。

重连会新建 SPAKE2 临时值和 AEAD 计数器。握手失败会清掉这一次的会话密钥，不会把上一次连接的计数器套到新密钥上。

## 测试

Linux 上 `crypto` 覆盖 SPAKE2 向量、AEAD 往返、重放、乱序、错误口令后密钥被清除、0.4.x / 未知版本拒绝，以及锁定时间表。`peer` 覆盖回环、绑定地址、第二会话、失败锁定、一次性密钥、重连和最多 3 帧在途。不需要 Windows IDD 或真机。
